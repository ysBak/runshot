## 회원가입 401에 대한 판단

기준 저장소에는 이미 `POST /api/users`와 `POST /api/auth/login`의 `permitAll` 설정 및 로그인/JWT 구현이 있었습니다. 따라서 과거 회원가입 401의 원인을 현재 코드에서 재현·확정하지 못했습니다. 수정본은 실제 HTTP 테스트에서 토큰 없는 정상 회원가입 201, 잘못된 요청 400, 중복 409를 반환했습니다. 원인을 확인하지 않은 상태에서 과거 문제가 특정 한 줄 때문이었다고 단정하지 않습니다.

현재 코드에서 확인하고 수정한 문제는 러닝 생성 시 `record.user` 대입 누락, 소유자 검증 없는 CRUD, 엔티티 직접 반환, 수정 입력값 검증 누락, 웹 화면 접근 미허용 및 JSON 오류 응답 부재입니다.

## 검증하지 못한 항목 / 배포 조건

- 실제 사용자의 기존 MySQL 스키마·데이터 마이그레이션: DB 미제공. 사전 점검 SQL을 준비했습니다.
- Docker 이미지 빌드 / Compose 실제 기동: 이 환경에 Docker가 없습니다. Java JAR와 실제 MySQL 조합은 별도로 검증했습니다.
- 브라우저에서 회원가입·로그인·CRUD 전체 흐름: 로그인/회원가입 화면의 표시·탭 전환만 확인했으며, 인증 이후의 브라우저 통합 검증은 미완료입니다. API 시나리오는 실제 서버에서 직접 실행했습니다.
- 운영 HTTPS 백엔드·TLS·Sites 연결 및 운영 E2E: 백엔드 실행 서버/주소가 제공되지 않아 미완료입니다.
- 사진 업로드: 이번 변경 범위에 포함하지 않았습니다.

Sites는 Workers 환경이므로 Java/Spring Boot/MySQL을 직접 실행할 수 없습니다. 준비한 Sites Worker를 실제 서비스로 사용하려면 지속 실행되는 HTTPS Spring Boot 서버와 MySQL이 필요합니다. `RUNSHOT_API_URL` 및 같은 `RUNSHOT_GATEWAY_KEY`를 양쪽에 설정한 뒤, 소유자 전용 비공개 배포와 운영 검증을 마쳐야 합니다. 미설정 503 상태를 정상 작동하는 배포로 안내하지 않습니다.
